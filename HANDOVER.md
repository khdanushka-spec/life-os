## Key decisions

- **Dual auth architecture, deliberately decoupled**: Supabase email/password for regular users (`/login`, `/signup`, `(app)` route group) vs. fully local username/password for Super Admin (`/admin/login`, `(protected)` route group under `/admin`). They share the same `User` table (with `role` column) but nothing else — this was an explicit user requirement so Email/Google/Apple/Passkeys can be added for regular users later without touching admin auth. Full writeup in README's "Authentication" section.
- **Sessions are DB-backed, not JWT**, for the admin side — a random token lives in an httpOnly cookie, only its SHA-256 hash is stored server-side, 30-day sliding expiration. See `src/lib/auth/session.ts`.
- **Proxy (Next 16's renamed middleware) does cheap/optimistic checks only** — cookie presence for admin routes, Supabase session refresh for regular routes. The *authoritative* check (DB lookup, role check) always happens in the relevant layout/page, matching Next's own guidance against slow work in Proxy.
- **AI provider priority is Ollama → Anthropic → OpenAI**, resolved fresh on every request (`src/lib/ai/providers.ts`, `resolveAiModel()`). This isn't arbitrary: Ollama at `localhost:11434` is architecturally *only* reachable from a machine actually running it, so on Vercel it always fails its 800ms reachability check and falls through automatically — no environment-specific branching needed. This means `/ai` **must** be `export const dynamic = "force-dynamic"` or Next bakes in a stale provider choice at build time (this was a real bug, already fixed).
- **`User` row resolution is find-by-id → find-by-email → create-with-race-fallback**, not a naive `upsert({where: {id}})`. Both `email` and `id` are unique constraints; a naive upsert can hit the email constraint if a row already exists under a different id, or lose a race when multiple routes fire concurrently on first login (this actually happened — see `src/server/db-user.ts`'s comment block for the full reasoning).
- **Everything that depends on an external service being configured degrades gracefully instead of crashing** — Supabase unconfigured → "preview mode" with mock data; no AI provider → friendly alert instead of a broken chat. This pattern is used everywhere (`isSupabaseConfigured()`, `resolveAiModel()` returning `null`) and should be followed for any new module.

  - `ANTHROPIC_API_KEY` is still `[SENSITIVE]` locally — the real value was never obtained (user added it to Vercel directly; local testing of the Anthropic path was never actually done, only inferred from production behavior + a "Claude" badge screenshot from the user).
- **Bash's working directory sometimes silently resets to `C:\Users\dnand`** (home) between tool calls instead of staying in `aura-os`. Always prefix with `cd /c/Users/dnand/aura-os &&` rather than assuming cwd persisted.
- **Two Vercel projects exist for this one GitHub repo**: `life-os-k9g4` (real — has all the env vars, this is the one to use) and `life-os` (empty duplicate, never cleaned up — low priority but the user knows about it).
- **Prisma has a built-in AI-agent safety guard**: `prisma db push --accept-data-loss` refuses to run when invoked by an AI agent unless `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION=<exact user consent text>` is set. Needed once this session for the `username` unique-constraint addition; the user said "yes" and that exact text was passed as the env var value. Expect this to trigger again on future schema changes involving new unique constraints or column drops — stop and ask before working around it.
- **The auto-mode classifier also independently blocks**: raw SQL writes to Supabase's `auth.*` schema (even simple ones like manually confirming a test email), and direct edits to production Vercel env vars — both require explicit user "yes" first. Prisma Client operations (`.create()`, `.delete()`, etc.) on our *own* tables are not blocked this way.
- **Supabase's built-in email sender has a low rate limit** that blocked real signup/confirmation testing repeatedly this session. Never resolved — custom SMTP setup in Supabase Auth settings would fix it permanently, user hasn't done this yet. Several unconfirmed test accounts exist in Supabase auth as a result: `aura-os-verify-8k2p@mailinator.com`, `aura-os-e2e-p7q3@mailinator.com`, `aura-os-review-q9z2@mailinator.com`, `aura-os-final-m3x8@mailinator.com` — safe to ignore or delete via Supabase dashboard.
- **The user does now have one working confirmed regular-user Supabase account** (seen logged in via screenshot, avatar initials "DH") — its email is unknown to me, they confirmed it themselves outside this session's visibility.
- **Base UI (`@base-ui/react`, shadcn's "base-nova" style used throughout this project) uses a `render` prop, not Radix's `asChild`** — e.g. `<DropdownMenuItem render={<button type="submit" />}>`. Getting this wrong causes nested-interactive-element bugs.
- **AI SDK v7 specifics** (this project is on `ai@7.0.37`, notably newer than most training data): `convertToModelMessages()` returns a `Promise` (needs `await`); `useChat` lives in `@ai-sdk/react`, not `ai`; response conversion is `.toUIMessageStreamResponse()`, not the older `.toDataStreamResponse()`; `sendMessage({ text })` not `append()`.
- **`server-only`-guarded modules can't be imported by plain `tsx`/`node` scripts** outside Next's bundler (it throws unconditionally). For any future standalone verification script, inline the logic instead of importing from files that `import "server-only"`.
- **Browser automation quirk**: synthetic `.click()` via the browser tool sometimes doesn't register on Base UI components (theme toggle, sheet triggers) — if a click seems to do nothing, retry via `javascript_tool` dispatching a real DOM `.click()` with proper input events before concluding something is broken.
- **Background bash polling loops using `grep -qE "Ready|Error"` in an until-loop have exited early on false/empty matches** multiple times this session (a tooling quirk, not a real state change) — always double-check with a direct, unfiltered `vercel ls` before trusting a loop's exit.
